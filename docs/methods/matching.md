# Подбор вакансий под резюме

Задача: по тексту резюме вернуть вакансии, на которые человеку стоит откликнуться. Сравниваются лексический поиск, две эмбеддинг-модели, их слияние с лексическим поиском и реранкер-кросс-энкодер, все на одних и тех же синтетических резюме и одном пуле вакансий.

Код `src/radar/models/matching.py` (поиск, метрики, функция для API), `src/radar/models/matching_data.py` (пул, резюме, разметка), `src/radar/models/matching_embed.py` (эмбеддинги и реранкер на CPU в WSL). Конфиг `configs/matching.toml`, результат `results/models/matching.json`.

## Пул

Все IT-сущности дедупа порталов (trudvsem API и снимки, Хабр Карьера, SuperJob), у последней записи которых есть валидные поля студента и роль не `non_it`: <!--n:models/matching.json:metrics.data.pool.value:,d|ru-->11 124<!--/n--> вакансии, из них открыты на последний день сбора <!--n:models/matching.json:metrics.data.pool_open_now.value:,d|ru-->6 124<!--/n-->. Текст вакансии это вход экстрактора (`radar.extract.inputs.input_for_record`): заголовок, шапка фактов (зарплата, адрес, опыт, занятость) и текст. Оценка идёт по всему пулу, API по умолчанию возвращает только открытые.

## Синтетические резюме

Резюме в проекте нет, поэтому они построены из вакансий. Для вакансии-затравки берутся её поля, извлечённые студентом, и из них по шаблону пишется короткое резюме:

- желаемая должность из фиксированного списка названий для роли схемы (для `backend` это «Backend-разработчик» или «Серверный разработчик»), с грейдом, если он извлечён;
- опыт работы из минимального требуемого опыта;
- навыки: случайные 60-100% навыков затравки плюс до двух навыков, частых для этой роли в пуле;
- город затравки и готовность к удалённой работе, если вакансия удалённая;
- один из трёх шаблонов порядка строк.

Из текста вакансии в резюме не попадает ни одно слово, кроме названий навыков и города. Затравки это вакансии с хотя бы тремя извлечёнными навыками. Они делятся на dev и test солёным хэшем id сущности: <!--n:models/matching.json:metrics.data.queries_dev.value:d-->300<!--/n--> резюме dev и 300 test. Всё выбирается на dev (модель, вес слияния, реранкер), test считается один раз командой с `--final-test`.

## Разметка релевантности

Релевантность вакансии для резюме задана правилом по полям обеих сторон до первого запуска поиска:

- 0, если не совпадает группа роли, грейды отличаются больше чем на шаг (неизвестный грейд совместим с любым) или не подходит место (вакансия не удалённая, у неё указаны города, и города резюме среди них нет);
- 2, если иначе и резюме покрывает хотя бы половину извлечённых навыков вакансии;
- 1 в остальных совместимых случаях.

У медианного резюме <!--n:models/matching.json:metrics.data.highly_relevant_median.value:.1f|ru-->12,5<!--/n--> вакансии с оценкой 2 и <!--n:models/matching.json:metrics.data.relevant_median.value:.1f|ru-->154,5<!--/n--> с оценкой 1 или 2.

Защита от утечек:

1. Резюме строится из полей, а не из текста вакансии, поэтому поиск не может найти затравку по совпадению формулировок.
2. Все системы читают только тексты (резюме и вакансии), а не поля, из которых построена разметка. Реранкер на полях (совпадение роли и навыков) по этой разметке выиграл бы по определению, поэтому он здесь не оценивается.
3. Вес слияния выбран на dev, test не трогался.

## Системы

- `bm25`: Okapi BM25 (k1 = 1,2, b = 0,75) по словам текста в нижнем регистре, без лемматизации.
- `dense_<модель>`: косинус нормированных эмбеддингов. Модели multilingual-e5-small и multilingual-e5-base (префиксы `query:` и `passage:`, среднее по токенам); вакансия обрезана до 512 токенов. BAAI/bge-m3 стоит в конфиге, но его эмбеддинги не считались: это 568 млн параметров против 278 млн у e5-base, а на CPU e5-base кодировал пул <!--n:models/matching.json:embeddings.intfloat/multilingual-e5-base.pool.seconds:,.0f|ru-->2 786<!--/n--> с.
- `rrf_<модель>`: reciprocal rank fusion эмбеддингов и BM25 (k = 60), без подбираемых параметров.
- `fusion_<модель>@<вес>`: взвешенная сумма стандартизованных по запросу оценок эмбеддингов и BM25; вес эмбеддингов выбран на dev из сетки 0,5-0,9.
- реранкер: первые 20 кандидатов отдаваемой API системы (`fusion_e5-small@70`, раздел «Что отдаёт API») пересортированы кросс-энкодером BAAI/bge-reranker-v2-m3 (вход резюме и текст вакансии, до 512 токенов), остальные остаются ниже в порядке первой стадии. На CPU это около <!--n:models/matching.json:metrics.dev.rerank.seconds_per_query_median.value:.0f-->25<!--/n--> с на резюме, поэтому реранкер оценён абляцией на первых <!--n:models/matching.json:metrics.dev.rerank.queries.value:d-->100<!--/n--> резюме dev, парно со своей первой стадией на тех же резюме.

## Метрики

На каждое резюме считаются nDCG@10 (выигрыш 2^rel − 1, идеальный порядок по всему пулу), MRR первой вакансии с оценкой 2 и полнота на 50 по вакансиям с оценкой 2 с ограничением знаменателя (найдено в топ-50, делённое на min(их число, 50), R_cap в BEIR). Интервалы 95% это бутстрап по резюме, 2000 повторов, seed в `configs/eval.toml`; разницы систем парные на одних и тех же повторах.

## Что отдаёт API

API (`/match`) отдаёт `fusion_e5-small@70`: лучшую систему dev среди тех, чей кодировщик помещается в контейнер API с лимитом памяти 1 ГБ (`[serving]` в конфиге: e5-small во float32 туда помещается, e5-base нет). По nDCG@10 она не отличима от лучшей системы dev (разница выше). Индекс с векторами пула лежит в `models/matching/index.pkl`, выбор в `models/matching/choice.json`. Реранкер в API не включён: <!--n:models/matching.json:metrics.dev.rerank.seconds_per_query_median.value:.0f-->25<!--/n--> с на запрос на CPU для онлайн-ответа слишком много, и прироста на dev он не дал.

## Ограничения

- Резюме синтетические: короткий список навыков по шаблону. Настоящие резюме длиннее и написаны свободным текстом, на них лексический поиск теряет часть преимущества точного совпадения названий навыков, а эмбеддинги могут выиграть.
- Разметка задана правилом по полям, извлечённым моделью, а не оценкой человека. Ошибка извлечения в вакансии становится ошибкой разметки; правило покрытия навыков не знает, что Django подразумевает Python.
- Вес слияния выбран на dev, поэтому число на dev для `fusion` оптимистично на величину выбора.
- Затравки с тремя и более навыками чаще с Хабра и SuperJob, чем в среднем по пулу; на коротких объявлениях trudvsem качество может быть другим.
